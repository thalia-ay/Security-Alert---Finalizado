11. Descubra como a chave final é formada

A partir da rotina do loader, a chave utilizada pelo RC4 fica composta por:

RC4KEY + RC4IV0 + RC4IV1

Portanto:

4c1fb7a3618a2d9e7b3ec0f52e9a64d1
+
9ea14f7c
+
f5d6823b

Resultado:

4c1fb7a3618a2d9e7b3ec0f52e9a64d19ea14f7cf5d6823b

São:

16 + 4 + 4 = 24 bytes

de chave utilizada pela implementação.

12. Faça a descriptografia em Python

Agora você pode reproduzir o algoritmo.

Crie:

nano decrypt.py

Cole:

from pathlib import Path


def rc4(data, key):
    S = list(range(256))
    j = 0

    # KSA - Key Scheduling Algorithm
    for i in range(256):
        j = (j + S[i] + key[i % len(key)]) & 0xff
        S[i], S[j] = S[j], S[i]

    # PRGA - Pseudo-Random Generation Algorithm
    i = 0
    j = 0

    output = bytearray()

    for byte in data:
        i = (i + 1) & 0xff
        j = (j + S[i]) & 0xff

        S[i], S[j] = S[j], S[i]

        keystream_byte = S[(S[i] + S[j]) & 0xff]

        output.append(byte ^ keystream_byte)

    return bytes(output)


encrypted = Path(".jujutsukskdsa").read_bytes()

key = bytes.fromhex(
    "4c1fb7a3618a2d9e7b3ec0f52e9a64d1"
    "9ea14f7c"
    "f5d6823b"
)

decrypted = rc4(encrypted, key)

Path("payload_decrypted.exe").write_bytes(decrypted)

print("Payload salvo como payload_decrypted.exe")
print("Primeiros bytes:", decrypted[:16].hex())

Salve.

Execute:

python3 decrypt.py

17. Agora descubra a técnica de execução

Volte para:

strings -a mshelp.exe

As APIs principais encontradas são:

CreateProcessA
GetThreadContext
SetThreadContext
ResumeThread
VirtualAllocEx
WriteProcessMemory
ReadProcessMemory
NtUnmapViewOfSection
NtQueryInformationProcess

Observe a sequência.

CreateProcessA cria um processo.

GetThreadContext recupera os registradores da thread.

NtQueryInformationProcess permite obter informações sobre o processo/PEB.

ReadProcessMemory lê memória do processo.

NtUnmapViewOfSection remove a imagem original.

VirtualAllocEx aloca memória dentro de outro processo.

WriteProcessMemory escreve o payload nesse processo.

SetThreadContext altera o contexto da thread.

ResumeThread inicia a execução.

Esse conjunto é característico de Process Hollowing.

24. Procure CreateProcessA

No Ghidra:

Search
→ For Strings

ou pelo Symbol Tree, procure:

CreateProcessA

Depois:

References To

Você deverá encontrar a chamada que cria o processo hospedeiro.

O detalhe essencial é verificar se existe:

O valor dessa flag é:

0x00000004

Isso significa que o processo é criado mas sua thread principal não começa imediatamente.

Esse comportamento é essencial para Process Hollowing.

25. Depois procure NtUnmapViewOfSection

A função:

NtUnmapViewOfSection

remove uma região mapeada do processo remoto.

No contexto encontrado:

notepad.exe

é criado e sua imagem original é removida.

Então há literalmente a etapa de "esvaziamento" do processo — daí o nome:

Process Hollowing.

26. Procure VirtualAllocEx

Em seguida:

VirtualAllocEx

é utilizada para reservar memória dentro do processo notepad.

Provavelmente você encontrará parâmetros relacionados a:

ImageBase
SizeOfImage
MEM_COMMIT
MEM_RESERVE
PAGE_EXECUTE_READWRITE

ou valores equivalentes.

27. Procure WriteProcessMemory

Essa API mostra onde o loader realmente transfere o PE.

Pode haver uma gravação para:

PE headers

e diversas gravações para:

sections

O próprio executável possui mensagens como:

Write headers falhou
Write sec

Ou seja, o loader aparentemente realiza algo semelhante a:

WriteProcessMemory(
    processo,
    nova_base,
    headers,
    SizeOfHeaders
);

e depois:

for cada section:
    WriteProcessMemory(...)

Isso é um mapeamento manual da imagem dentro do processo remoto.

28. Atualização do PEB

Uma das strings mais importantes é:

PEB.ImageBaseAddress atualizado=

O PEB é o:

Process Environment Block

Dentro dele existe a informação:

ImageBaseAddress

Como a imagem original do notepad.exe foi removida e substituída, o loader atualiza esse endereço.

Isso reforça ainda mais a identificação de Process Hollowing.

29. Alteração do RIP

Existe outra string muito importante:

SetThreadContext Rip=

Em x64:

RIP

é o registrador que aponta para a próxima instrução a ser executada.

O loader normalmente calcula:

novo ImageBase + AddressOfEntryPoint

e coloca esse valor no:

RIP

Então:

RIP = PayloadImageBase + AddressOfEntryPoint
30. Finalmente ResumeThread

A última etapa é:

ResumeThread

O processo havia sido criado suspenso.

Depois de:

desmapear notepad
→ alocar memória
→ escrever payload
→ ajustar PEB
→ mudar RIP

ele executa:

ResumeThread

A thread começa a executar, mas agora o entry point não é mais efetivamente o código original esperado do notepad.

É o payload.
